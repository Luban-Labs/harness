# ADR 格式

译自 mattpocock/skills 的 ADR-FORMAT。ADR 放 `docs/adr/`,顺序编号:`0001-slug.md`、`0002-slug.md`……目录懒创建,第一条 ADR 需要时才建。编号:扫 `docs/adr/` 取最大号加一。

## 模板

```md
# {决策的短标题}

{1-3 句:背景是什么、决定了什么、为什么。}
```

就这些。一条 ADR 可以只有一段;价值在于记下**做过**这个决定和**为什么**,不在于填满章节。

## 可选节(多数 ADR 不需要)

- **Status** frontmatter(`proposed | accepted | deprecated | superseded by ADR-NNNN`):决策会被重新审视时才加。
- **Considered Options**:被否的方案值得记住时才加。
- **Consequences**:有不显然的下游影响要点明时才加。

## 什么时候提议写 ADR

三条**必须同时**成立:

1. **难逆转**:以后改主意代价明显。
2. **无上下文会费解**:将来的读者看代码会想「到底为什么这么干」。
3. **真实权衡的结果**:确有备选,为具体理由选了这个。

容易逆转的跳过,到时候直接改就是;不令人意外的没人会问为什么;没有真正备选的,除了「我们做了显然的事」没什么可记。

### 什么算数

- **架构形状。**「我们用 monorepo」「写模型事件溯源,读模型投影到 Postgres」。
- **context 之间的集成方式。**「Ordering 和 Billing 通过领域事件通信,不走同步 HTTP」。
- **带锁定的技术选型。** 数据库、消息总线、认证提供方、部署目标;不是每个库,只是换掉要一个季度的那些。
- **边界与归属。**「客户数据归 Customer context,其他 context 只按 ID 引用」。明确的「不」和「是」一样值钱。
- **刻意偏离显然做法。**「用手写 SQL 不用 ORM,因为 X」。任何一个合理读者会假设相反的地方——防止下一个人把它「修」回去。
- **代码里看不见的约束。**「合规原因不能用 AWS」「合作方 API 契约要求 200ms 内响应」。
- **否决理由不显然的备选。** 考虑过 GraphQL 最后因微妙原因选了 REST,记下来;否则半年后有人再提。
