# interview-me

采访式需求澄清:owner 先讲,你判断构思的完成度,只追问真挡路的细节、一次一个,采访完对齐需求,再自己判要不要出 spec。改自 mattpocock/skills 的 grilling,去掉「对不齐就一直追问」;记文档、出 spec、切 ticket 沿用他的 grill-with-docs、to-spec 与 to-tickets,在 `references/`,**要不要做由你判,不等 owner 说**。

## 何时用 / 何时不用

- 用:owner 讲了一个想做的东西,目标、范围、验收三者至少一项还说不清。
- 用:owner 说「采访我」「先问我」「你看还缺什么」。
- 不用:owner 已给出具体文件与改法,直接做;已有 spec,按该文档走;只是在问问题,不是要做东西;owner 说「建个 Task」「记个 bug」这类自己已经确定的事,按 docs/rules/harness.md 直接建 Task,不采访。

## 做法

1. **先听完,再看仓库。** owner 描述时不打断、不提问。讲完后把听到的摆成四格:目标一句 / 范围与不做 / 验收演示 / 未知,每条标明是 owner 说的还是你推的。同时看一眼仓库有没有 `CONTEXT.md`、`CONTEXT-MAP.md`、`docs/adr/`:有,采访全程按 [with-docs.md](./references/with-docs.md) 做;没有,先不建,等第 2 步出现触发条件再按它懒创建。
   判据:四格里没有一条是你替 owner 补的答案;推的都标了「推」。
2. **判完成度,只问挡路的。** 把「未知」分两类:不问就定不了范围或验收的 → 挑当前最挡路的**一个**问;其余 → 写上你的推荐默认值、标「推」,不问。格式:

   ```
   ❓ <问题>
   ➡️ 推荐:<你的答案>;备选:<一两个>
   ```

   事实归你查(文件、代码、工具),不问 owner 能自己查到的事;决策归 owner。
   采访中出现下面任一情况,就按 with-docs.md 当场处理,不用问 owner 要不要:owner 用的词与 `CONTEXT.md` 冲突、用了含混或多义的词、两个词指同一物、说法与代码矛盾、出现同时满足 ADR 三条门槛的决策。
   判据:一条消息里只有一个 ❓;这条不问就定不了范围或验收。
3. **每答一条重画四格,回第 2 步。** 挡路的未知清零、或 owner 说「够了」「先这样」,进第 4 步。
   判据:不追问「以后要不要扩展」「要不要兜底」这类 owner 没提的事;每轮推荐默认值的条数多于提问的条数。
4. **对需求。** 用四格向 owner 复述一遍,问「是这个意思吗」;owner 确认前不动手。
   判据:复述里每条能指回 owner 原话、你查到的事实、或标了「推」的默认值。
5. **自己判出口,一行说明,不问 owner 选。** 按可观察条件判,命中靠前的优先:
   - 大 → 走 [to-spec.md](./references/to-spec.md):命中 docs/rules/harness.md「何时建 Task」三条之一,第 3 条现在已能看出会命中也算。新组件或新依赖另过 /kickoff,不因此出 spec。
   - 中 → 先列 `[step] → 执行者 → verify: [check]`,再做:多步或多文件,但三条都没中。
   - 小 → 直接做:改动范围一句话说得清。
   写成「判定:大 / 出 spec,因为 <命中哪条>」放在对齐结论末尾;owner 一句话就能改判,改了照改后的走。
   判据:判定引用的是命中的条件,不是「我觉得」。

## 检验

- 全程 ❓ 总数不超过「挡路未知」的条数;从没有一轮同时问两个问题。
- 对需求那一段,一个没看过对话的人能照着做。
- 出口判定一行、带命中条件,在对齐结论末尾;是否记文档、是否出 spec,全程没有向 owner 问过「要不要」。
